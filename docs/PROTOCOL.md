# SEVER-1 / WSS и Linux obfs4-адаптер — 0.3.0

В 0.3.0 Python дополнительно принимает `transport=obfs4`: внешний PT скрывает
внутренний TLS-поток, после TLS клиент отправляет AUTH как первый кадр.
Формат кадров тот же; кадры читаются из потока без WebSocket-границ. Детали,
профиль и непроверенные части описаны в [LOOK_LIKE_RANDOM.md](LOOK_LIKE_RANDOM.md).
Далее описан сохранённый WSS-режим, используемый и мобильными исходниками.

Экспериментальный протокол передачи IPv4. Wire version остаётся 1, но внешний транспорт и формат профиля изменились. Профиль v1 и сырой TCP/TLS не поддерживаются клиентами 0.2.0.

## Внешнее соединение

1. Клиент открывает `wss://host:port/path` с TLS 1.3, проверяя системное доверие и имя сервера.
2. Выполняется настоящий HTTP/1.1 WebSocket Upgrade с `Authorization: Basic base64(user:token)`. Секрет передаётся только внутри TLS. Токен генерируется из 32 случайных байтов; Basic здесь — упаковка bearer-подобных учётных данных, не дополнительное шифрование.
3. На публичной стороне nginx проверяет авторизацию через локальный backend. Без действующего профиля запрос обслуживает обычный статический сайт. nginx не должен добавлять Authorization в логи.
4. Backend повторно проверяет авторизацию, принимает WebSocket и передаёт данные внутреннему Gateway. Первый AUTH формируется **внутри сервера** из проверенного заголовка; клиент не отправляет AUTH в бинарном сообщении.
5. После получения CONFIG клиент поднимает TUN. Данные передаются бинарными сообщениями WebSocket: **один кадр SEVER на сообщение**. Сжатие permessage-deflate сервером не согласовывается.

Backend слушает только loopback. Публичное TLS-соединение завершается на nginx, которому доверяются секреты и трафик. Между nginx и backend используется HTTP на том же узле. Для разделения по разным узлам требуется другой защищённый канал; такая конфигурация не подготовлена.

Клиенты не выполняют откат на raw TLS и не имеют skipVerify. Python/Android запрещают HTTP redirects; в iOS предусмотрен отказ через URLSession delegate, но его фактическое поведение ещё не проверено на устройстве. Браузерный fingerprint не имитируется. Android использует OkHttp, iOS — URLSession, Python — aiohttp.

## Внутренний кадр

Все целые big endian, заголовок внутри WebSocket/TLS.

| Смещение | Размер | Поле | Ограничение |
|---|---:|---|---|
| 0 | 1 | version | 1 |
| 1 | 1 | kind | 1..6 |
| 2 | 2 | payload_length | 0..4096 |
| 4 | 2 | padding_length | 0..511 |
| 6 | 2 | reserved | 0 |
| 8 | payload_length | payload | По типу |
| далее | padding_length | padding | Случайные байты |

Максимум сообщения — 4615 байтов. Получатель проверяет размеры, тип, версию и отсутствие лишних байтов. Текстовые WebSocket-сообщения отвергаются. Фрагменты самого WebSocket собирает библиотека до передачи сообщения кодеку.

**Padding:** независимая равномерная случайная длина 0..511. Округления до 256 больше нет. Средняя добавка — 255.5 байта на кадр плюс WebSocket/TLS/TCP/IP. Для маленьких IP-пакетов это существенный overhead. Равномерное распределение также может служить статистическим признаком; оно не доказано похожим на браузерный трафик.

| kind | Имя | Направление и назначение |
|---:|---|---|
| 1 | AUTH | Только внутренний ввод сервера после HTTPS-авторизации; по WSS повторный AUTH отклоняется |
| 2 | CONFIG | Сервер → клиент: JSON `ip`, `prefix:24`, `mtu:1280`, `dns` |
| 3 | PACKET | Оба направления: один IPv4-пакет 20..1280 байтов |
| 4 | PING | Клиент → сервер: 8 случайных байтов |
| 5 | PONG | Сервер → клиент: те же 8 байтов |
| 6 | CLOSE | Клиент → сервер: пустой payload |

Внешние WebSocket Ping/Pong/Close обрабатывает библиотека, отдельно от сообщений SEVER. Туннельная liveness-проверка использует SEVER PING/PONG.

## Служебные проверки

Вместо постоянного интервала 15 секунд:

- Ожидание без исходящих данных: случайно 20..35 секунд, затем PING.
- Передача IP-пакета переносит idle deadline.
- Для односторонних загрузок есть независимый предел 50..65 секунд между пробами: он не позволяет полностью прекратить проверку обратного направления.
- После PING оба интервала выбираются заново. Точная фаза зависит от трафика.
- Сервер ожидает полный входящий SEVER-кадр не более 90 секунд. Клиенты используют таймаут/контроль приёма 90 секунд; nginx proxy timeout — 120 секунд.

Это не постоянный фоновый поток фиктивного трафика. Рисунок служебных сообщений остаётся исследуемым признаком.

## Сеть и доверие

Сервер `10.77.0.1/24`, устройства `10.77.0.2..254`, один профиль — одна сессия. Сервер хранит SHA-256 токена, проверяет адрес источника IPv4 и запрещает непубличные/мультикаст назначения. Очередь одного клиента — 128 кадров. При перегрузке пакеты отбрасываются.

Мобильный IPv6 захватывается и отбрасывается; полноценного IPv6-туннеля нет. Отсутствие утечек на ОС ещё требуется проверить. Резервные серверы должны знать тот же user/token/IP и обслуживать указанный WSS path. Автозагрузка endpoints отсутствует.

TCP-over-TCP и блокировка последующих данных при потере ранних сегментов сохраняются. QUIC, UDP-транспорт, бесшовная миграция и поиск оптимального RTT не реализованы.

## Оставшиеся признаки

IP и DNS/SNI, особенности TLS клиента, длительность сессий, размеры/направления/тайминги, поведение под нагрузкой, повторное использование endpoint. Привязка HTTP-ошибок к состоянию backend может дать дополнительные отличия. Два локальных теста не исчерпывают активное зондирование.

Стандарты: [TLS 1.3](https://www.rfc-editor.org/rfc/rfc8446), [WebSocket RFC 6455](https://www.rfc-editor.org/rfc/rfc6455). Конфигурация frontend следует [nginx WebSocket proxying](https://nginx.org/en/docs/http/websocket.html) и [auth_request](https://nginx.org/en/docs/http/ngx_http_auth_request_module.html).
