# SEVER через obfs4 — экспериментальный Linux-адаптер, 10.09.2026

## Что означает требование

Цель — случайный на вид внешний поток, включая установление соединения, без
открытого заголовка SEVER и внешнего TLS ClientHello. Это не тождественно
«неопределяемому трафику». Название конкретного протокола и решение заблокировать
неизвестный шифрованный поток — разные задачи классификатора.

Исследование [USENIX Security 2023](https://gfw.report/publications/usenixsecurity23/en/)
описывает пассивное обнаружение и блокировку fully encrypted traffic в Китае,
включая obfs4. Отсутствие знакомого протокола вместе со статистикой первых данных
может само служить признаком. Это контрпример к гарантии невидимости, а не описание
актуальных правил российских ТСПУ. Размеры, направления, интервалы, длительность
соединений и адрес сервера также остаются наблюдаемыми.

## Реализованный путь

Linux SEVER-клиент → локальный SOCKS5 obfs4-клиент → сеть → obfs4-сервер →
закрытый TLS-бэкенд SEVER на 127.0.0.1:8788.

Внешнюю обфускацию выполняет **отдельно установленный obfs4proxy/совместимый PT**.
Архив не содержит его бинарник, не скачивает его и не реализует заново его
криптографию. [Спецификация obfs4](https://raw.githubusercontent.com/Yawning/obfs4/master/doc/obfs4-spec.txt)
описывает аутентифицированное установление ключей, Elligator для представления
открытых ключей, сокрытие длин кадров и изменение рисунка потока. Защита от
зондирования имеет условия, в частности доступность параметров моста противнику.
Произвольный XOR, новое имя или просто добавление padding этого не заменяют.

Собственная часть остаётся SEVER-1. Это **не новый мировой протокол обфускации**.
Сравнение obfs4 с WSS по обнаруживаемости пока не выполнено.

В адаптере:

- Профиль v2 принимает `transport=obfs4`; WSS выбирается отдельным профилем.
- Локальный proxy обязан иметь числовой loopback-адрес. SOCKS5 передаёт `cert`
  и `iat-mode`; согласование без этих аргументов отклоняется.
- Мост задаётся числовым IPv4/IPv6-адресом, без локального разрешения его DNS-имени.
- После создания PT-канала внутри него устанавливается TLS 1.3 с проверкой CA и
  `server_name`. Затем отправляется SEVER AUTH и начинается передача кадров.
- Бэкенд разрешает только loopback bind. Его нельзя публиковать через обычный
  TCP forward или отдельный публичный порт, обходящий obfs4.
- Неуспех закрывает соединение; попытки следующих мостов снова идут через PT.
  Автоматического перехода к прямому TLS или WSS нет.

Доверие локальному PT обязательно: приложение проверяет loopback-адрес и протокол
SOCKS, но не может доказать, что произвольный процесс на этом порту действительно
выполняет obfs4. Это должен обеспечивать запуск проверенного бинарника и его
конфигурация. `cert` obfs4 — параметры моста, а не X.509-сертификат внутреннего TLS.

## Подключение в лаборатории

Требуются установленный совместимый obfs4 PT на обеих машинах, Python-зависимости
проекта и отдельный тестовый сервер. Команды PT ниже — **не испытанные здесь
шаблоны**. Проверяйте вывод запуска вашей реализации; её версии могут отличаться.
Интерфейс родительского процесса описан в
[Tor PT specification](https://spec.torproject.org/pt-spec/index.html), сообщения
готовности — в [PT IPC](https://spec.torproject.org/pt-spec/ipc.html).

1. Создайте пользователя обычным `tools/provision.py`, как в LINUX.md. Подготовьте
   TLS-сертификат и ключ. Для private CA передавайте её через `--ca` клиенту;
   отключать проверку имени или сертификата не требуется.
2. Остановите прежний SEVER-бэкенд при использовании того же TUN. В этой версии
   два независимых Gateway нельзя запускать на один TUN и один пул адресов.
3. Запустите приватный бэкенд с привилегиями для TUN:

```bash
.venv/bin/python -m sever.pt_backend --users users.json --cert server.crt --key server.key
```

4. На сервере создайте защищённый каталог состояния и запустите внешний PT в
   отдельном терминале. Используйте свободный публичный порт; 443 уже может быть
   занят nginx. Пример с 8443:

```bash
mkdir -m 700 pt-server-state
env TOR_PT_MANAGED_TRANSPORT_VER=1 \
  TOR_PT_STATE_LOCATION="$PWD/pt-server-state" \
  TOR_PT_SERVER_TRANSPORTS=obfs4 \
  TOR_PT_SERVER_BINDADDR=obfs4-0.0.0.0:8443 \
  TOR_PT_ORPORT=127.0.0.1:8788 \
  obfs4proxy
```

Это отдельный запуск PT без Tor daemon. Не наследуйте посторонние `TOR_PT_*`
переменные из окружения Tor. Получите `cert` и `iat-mode` из `SMETHOD`/созданного
bridge-файла вашей реализации. Сохраните каталог состояния: его замена меняет
идентичность моста. Публичный firewall разрешает PT-порт, бэкенд остаётся локальным.

5. На Linux-клиенте запустите PT отдельно и дождитесь `CMETHOD obfs4 socks5` и
   `CMETHODS DONE`. Возьмите фактический loopback-порт из вывода, он не фиксирован:

```bash
mkdir -m 700 pt-client-state
env TOR_PT_MANAGED_TRANSPORT_VER=1 \
  TOR_PT_STATE_LOCATION="$PWD/pt-client-state" \
  TOR_PT_CLIENT_TRANSPORTS=obfs4 \
  obfs4proxy
```

6. Создайте отдельный профиль из выданного v2-профиля. Адрес документационный,
   имя и cert ниже — заполнители; команда требует настоящие значения:

```bash
.venv/bin/python tools/obfs4_profile.py wss.profile.json \
  --out obfs4.profile.json --bridge-ip 192.0.2.10 --bridge-port 8443 \
  --server-name vpn.example.com --obfs4-cert REPLACE_WITH_BRIDGE_CERT \
  --iat-mode 0 --proxy-port 12345
.venv/bin/python tools/probe_obfs4.py obfs4.profile.json --samples 10
.venv/bin/python -m sever.client obfs4.profile.json
```

`iat-mode` берите из конфигурации моста; большее число не является доказательством
лучшей маскировки. Конвертер сохраняет user/token, создаёт файл mode 0600 и не
изменяет исходный профиль. Probe проверяет CONFIG и PING/PONG без TUN. Его
успех не доказывает, какой процесс стоит за локальным SOCKS, и не измеряет DPI.

Маршруты/NAT настраиваются по LINUX.md. Для этого режима исключайте из VPN-маршрута
**IP самого obfs4-моста**: внешний сокет принадлежит отдельному процессу PT.
Сохраните блокирование IPv6 вне поддержанного туннеля. Тесты с TUN в памяти не
подтверждают отсутствие утечек в реальной ОС.

## Проверка и границы результата

`tests/test_obfs4_adapter.py` использует SOCKS-заглушку на loopback, которая
пересылает настоящий TLS. Это намеренно **не эмулятор obfs4 или ТСПУ**.
Проверяются аргументы, фрагментированный SOCKS-ответ, CONFIG, IPv4 в обе стороны,
PING/PONG, отклонение неверного токена и TLS-сертификата, отказ от прямого обхода
PT, ограничения профиля и адреса бэкенда.

В этой среде obfs4proxy/lyrebird отсутствуют. **Внешний obfs4 handshake, захват
реального obfs4-потока, зондирование, iat-mode и совместимость двух настоящих PT
не проверены.** Android/iOS поддерживают только прежний WSS: для obfs4 требуются
нативный PT-движок и интеграция сокетов с VpnService/Network Extension. Запуск
десктопного процесса из мобильного приложения не является готовым решением.

Для заявления «менее обнаруживаемый» необходим следующий эксперимент:

1. Испытать два настоящих PT локально и снять внешний pcap; убедиться, что наружу
   не выходит TLS ClientHello, SEVER AUTH или обычный SOCKS.
2. Проверить неавторизованное зондирование, повторы handshake и неверные параметры;
   учитывать ответы, время закрытия и нагрузку на сервер.
3. Сравнить WSS и obfs4 при одинаковой прикладной нагрузке, разных серверах и днях;
   измерить скорость, RTT, накладные расходы и на устройствах расход батареи.
4. Обучить независимый классификатор и проверить на отложенных серверах/днях.
   Публиковать TPR при фиксированном FPR, состав обычного трафика и доверительные
   интервалы; одной энтропии или отсутствия известной сигнатуры недостаточно.
5. Измерить доступность в сетях нескольких российских операторов, с контрольными
   соединениями. Этот результат относится только к проверенным сетям и времени.

Чисел обнаруживаемости и гарантии обхода ТСПУ в этом выпуске нет.
